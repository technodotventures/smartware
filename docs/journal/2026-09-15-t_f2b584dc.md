# DECIDE: the revocation boundary is the grant row — one row per (actor, client), and the re-grant requirement (ADR-0012)

## Intent

Decide the ADR-0011 §6 finding `grant-row-revocation` (gate run card `t_9740ae98`,
checks 6a/6c/6n): `FORGET.SCOPE` revokes every grant **row** whose capability arrays
reference the scope (spec §10b.3), and the adapter has no re-grant surface — so in
the Coffee tenant model (one grant per actor listing all their clients) erasing one
client silently removes that staff member's access to their **other** clients.
Three options were on the card: (a) keep row-scoped revocation and make provisioning
narrow (per capability/scope), (b) narrow the revocation in the substrate, (c) add
an adapter re-grant path. Deliverable for (a): the written decision, the conformance
tests it implies, and the doc/handoff text change — **no implementation beyond that**.
Out of scope: substrate behaviour changes, and the published protocol surface.

## What was done

  Status: Accepted): the substrate keeps row-scoped revocation exactly as released;
  provisioning issues **one grant row per (staff actor, client scope)**, so the
  revocation boundary equals the intended access boundary by construction.
- **Measured the decision instead of asserting it** (`scripts/scratch-f2b584dc-measure.mjs`,
  deleted from the tree; kept in the evidence dir as `measure.mjs`; raw output
  `raw.log`, facts `measure.json`). On the **public adapter + package surface**,
  Node v26.5.1, in-process:
  - **S1 — shipped shape** (one row, `sam[meridian, arcadia]`): erasing `arcadia`
    → `grants_revoked: 1`, the row is `status:'revoked'` with **both** scopes in its

  - **S2 — decision shape** (one row per client): erasing `arcadia` → `grants_revoked`

    `meridian` recall is `ok:true n:1` **with no re-provisioning**; `arcadia` is

  - **S3 — the sharp edge the shape exposes**: with two rows, a **standby** replica's

    row's client and `403 insufficient_permission` for the **second** row's client —

## Round 2 — review verdict `changes_requested` (what changed, and why)

The artifact review (card `t_102f3dfa`, round 1) cleared the decision, the
evidence and the handoff text, and blocked on one gap: the deliverable's sharp-edge
inventory was incomplete and the new §10b.2 rule ("first-match lookups are never an
authorization decision") was false as written.

- **The gap, re-measured here rather than taken on trust (S4, 24 facts, reproduced
  twice):** `src/session/policy.ts:96` (`resolveTrust()` → `getGrantForActor()` →
  `resolveCapabilities()`) is a **third** first-match site, on the public MCP
  surface (`smartware_session_start`, `src/mcp.ts:560`). With one row per client, a
  session requesting the **second** row's client returns `capabilities_granted: []`
  while `checkGrant` authorizes the actor on that scope and the adapter's recall on
  it answers `ok:true n:1`; caps and trust both follow the first row, so the same
  two rows swapped give `user_facing` vs `verified`. S4 also found two things the
  review's probe did not: omitting `requested_scopes` **masks** the defect (the
  default is every config scope, and the first row covers one of them — why it
  survived round 1), and a `quarantine: true` row that grants the requested scope is
  ignored by the session (S4E).
- **Routing decision (the review's correction 2, option (i)):** the session union is
  folded into `t_864a5900` as **companion change 3**, not deferred. The reason is
  causal: the per-client shape is what makes the session surface wrong, so shipping
  the shape without the union would introduce a known-wrong public surface. The fix
  is single-row-invariant (one row resolves exactly as today), so the released
  session surface — protocol contract v0.4.1 — does not move for conformant configs;
  `t_864a5900`'s "the substrate is NOT changed" preamble is amended for exactly this
  call site by a comment on that card.
- **Semantics decided here, not left to the implementer** (ADR-0012 §4): a
  capability is granted if **any** active row of the actor covers **any** requested
  scope; trust/quarantine take the **most restrictive** union across the actor's
  active rows. Provisioning must additionally keep `trusted`/`quarantine` uniform
  across an actor's rows (contract §7) — the restrictive union is the fail-safe for
  divergence, not a licence to mix.
- **Correction 3 (make the rule true or qualify it):** §10b.2's sentence now names
  its one live exception, the site, and the card that closes it; the journal's
  read-from-the-source list is split accordingly (the session path is now **measured**
  — S4, not asserted) and the same split is written into the evidence NOTES.md.

- **The re-grant procedure's retired-marker trap is now named but not yet asserted
  in the fixture.** An operator who follows the *old* obvious edit — re-activating
  the revoked row an `erasure` leaves behind — re-authorizes the purged scope

- **The session surface is the last known first-match derivation** and it is wrong
