# Retention sweep: an OperationId already consumed by another op is not matched, so the sweep reuses the id and the ops log ends up with two ops under one id (measured)

## Intent

## Why
Found by the reviewer of `t_06db00ce` (round 1, artifact lens) while auditing the new payload-identity
lookup. The card's own fix landed and is approved: a reused `operation_id` with a different
`scope`/`as_of` now returns `conflict`. This card is the *residual* of the same invariant, measured,
not a regression of anything (`handleExpireRetention` behaved this way before the fix too).
`handleExpireRetention` filters the ops log down to entries whose `op` is already `retention.expire`
*before* it matches payload identity (`src/protocol/retention.ts:192`):
```ts
const priorEntries = [...readAllOpLogEntries(deps.opsDir)]
.filter(entry => entry.operation_id === params.operation_id && entry.op === 'retention.expire');
```
An OperationId already consumed by a **different** op is therefore invisible to the sweep, while every
sibling writer treats the id as globally owned — they filter by `operation_id` alone and check `op` as
part of the match, so any mismatch is a `conflict`:
- `src/protocol/observe.ts:191-197`, `forget.ts:116-123`, `forget_scope.ts:239-246`, `reflect.ts:488-497`.
